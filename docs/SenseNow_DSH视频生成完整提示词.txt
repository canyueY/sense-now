《Sense Now：让 AI 真正看完一条视频》DSH 视频生成完整提示词

一、任务目标

请根据我同时提交的中文口播录音、最终口播文字稿、真实项目素材和本提示词，生成一条适合发布到 Bilibili 的横屏技术介绍视频。

项目名称：Sense Now
中文名称：见闻
视频标题：《Sense Now：让 AI 真正看完一条视频》
项目定位：字幕优先的长视频索引与按需多模态问答插件
目标时长：以口播录音为准，预计约 5～8 分钟

必须以口播录音作为唯一主时间轴：

1. 保留完整原声，不重新配音，不擅自改写口播观点。
2. 先对录音进行语音识别、停顿检测和语义分段，再安排镜头。
3. 允许剪除我明确标记的口误、重复和长停顿。
4. 不得为了卡时长强行加速人声或删除关键技术说明。
5. 画面必须逐句对应口播，不制作与内容无关的科技空镜。
6. 功能介绍不能只是静态 PPT，必须使用清晰、精美、流畅的函数模型和数据流动画。

二、输入素材及使用优先级

优先使用我提供的素材：

1. 口播录音：主时间轴和主音轨。
2. 最终口播稿：校正字幕、专有名词和口误。
3. 真实项目录屏：产品演示的最高优先级素材。
4. 真实项目截图：缺少录屏时使用。
5. Sense Now Logo 和品牌素材。
6. GitHub 仓库信息、原项目信息、LICENSE 和 NOTICE。
7. 我提供的参考画面和动效模板。

素材优先级：

真实录屏 ＞ 真实截图 ＞ 根据真实实现制作的简化 UI ＞ 标注“示意”的抽象界面 ＞ 生成式背景素材。

禁止伪造：

- 未实际执行的测试结果；
- GitHub Star、下载量或用户数量；
- 真实用户账号、头像和评论；
- 未完成的产品界面；
- 真实人物身份识别结果；
- Token、Cookie、签名 URL、个人路径及其他隐私信息。

如果缺少真实素材，应使用明确标注为“示意”的抽象 UI，不能伪装成真实产品截图。

三、输出规格

- 主版本：1920×1080，16:9，30FPS；
- 编码：H.264；
- 音频：AAC，48kHz；
- 输出一份带字幕版本；
- 输出一份无字幕版本；
- 另行输出校对后的简体中文字幕 SRT；
- 如能力允许，额外输出工程文件或可二次编辑的时间线描述；
- 片头不超过 6 秒；
- 片尾不超过 10 秒；
- 不用空镜、重复动画或慢速 Logo 强行凑时长。

四、整体视觉风格

采用 DARK-TECH、SWISS、KEYNOTE、GLASS 的混合风格：

- 深蓝黑或石墨黑背景；
- 主强调色为青蓝色；
- 辅助色为紫色；
- 成功状态使用柔和绿色；
- 待确认和预算提醒使用黄色或橙色；
- 错误和内容缺失使用克制的红色；
- 正文使用白色或浅灰色；
- 使用现代、简洁、清晰的二维或轻量 2.5D 动效；
- 画面应接近高质量开源项目发布视频，而不是廉价赛博朋克宣传片。

避免：

- 大量粒子、字符雨、扫描线和胶片噪点；
- 频繁故障、频闪、强烈色差和镜头抖动；
- 无法阅读的代码墙；
- 同一镜头堆叠过多动效；
- 每句话使用不同转场；
- AI 生成的乱码中文和乱码界面。

五、声音处理

1. 对口播执行适度降噪、去爆音、均衡和轻度压缩。
2. 保持人声自然，不进行夸张变声。
3. 背景音乐使用无歌词、轻量科技感、可商用或无版权风险的音乐。
4. 背景音乐不得盖住人声；技术讲解段进一步降低音量。
5. 问题发现段可增加轻微悬念；片尾可以轻松一些。
6. “那还得了”“纯纯冤枉鱼吗”等位置可以使用很轻的喜剧音效，但不要加入罐头笑声。
7. whoosh、点击、锁定、节点连接等音效必须克制并与画面同步。

六、字幕规范

1. 根据口播录音重新识别，并以最终口播稿校对。
2. 每屏最多两行，单行尽量不超过 18 个汉字。
3. 使用白字、细描边或深色半透明底。
4. 字幕放在底部安全区，不遮挡代码、按钮、时间轴和函数节点。
5. 关键词可以使用青蓝、紫色或橙色强调，但不要整句变色。
6. 以下技术词必须统一：

Sense Now、见闻、Mnemosyne 2.0、Agent、AI、OCR、ASR、VAD、evidenceId、revision、chunk、SRT、VTT、ASS、GitHub。

7. 草稿中的“所以11月晚上”应按语义校正为“所以那天晚上”；如果录音实际内容不同，以录音为准。

八、统一函数动画规范

所有函数节点采用同一套圆角卡片设计，包含：

- 普通句子之间直接剪切或使用镜头内动画，不增加转场。

质感：

- P02：Logo 聚合或三路证据汇聚；
- P06：证据和产品毛玻璃卡片；
- P07：Logo 扫光；

后处理：

- F08 闪白/闪黑全片最多两次，透明度不超过 0.3；
- 默认禁用 F01 颗粒、F04 强色差、F05 扫描线、F06 高光溢色和 F09 低帧抽帧。

十、剪辑与镜头节奏

1. 叙事段可以稍快，技术段必须给观众足够阅读时间。
2. 普通技术镜头保持约 3～7 秒。
3. 复杂流程可以保持 8～12 秒，但必须通过节点点亮、镜头移动或数据流动维持变化。
4. 每个镜头最多包含一个主元素动画、一个文字动画和一个辅助镜头/转场。
5. 画面中同时存在的重点不得超过三个。
6. 所有代码一次只突出约 3～8 行。
7. 所有文字、函数名、时间戳和按钮必须在手机端清晰可读。
8. 动画必须服务于解释算法，不能为了炫技牺牲理解。

十一、真实性与安全要求

1. “5 分钟”必须表现为 chunk 大小，不是读取上限。
2. 不暗示 OCR、ASR、VAD 每次都会同时运行。
3. 不暗示 VAD 会自动产生文字。
4. 不暗示 Token 或模型存在会自动授权 ASR。
5. 不暗示匿名 speaker 已经绑定到真实人物身份。
6. 不暗示当前版本已完成所有真实长视频实机验证。
7. 不将 stub、unit 或 synthetic 测试包装成真实媒体测试。
8. 不在画面中泄露真实 Token、Cookie、签名 URL、用户名、私人路径或个人信息。
9. 保留原开源项目来源、LICENSE 和 NOTICE。
10. 如果口播中的工程数字与我提供的最新真实素材冲突，先使用最新真实素材，并在交付说明中标注冲突，不擅自伪造统一结果。

十二、交付前检查

导出前逐项核对：

1. 是否完整解释“8 分钟只读取约 3 分钟”的问题；
2. 是否明确“5 分钟是 chunk，不是读取上限”；
3. 是否展示字幕来源优先级；
4. 是否表现字幕变化后才调用 OCR；
5. 是否说明 VAD 和 ASR 独立授权；
6. 是否展示 Agent 先检索全片，再按需补看或补听；
7. 是否展示 evidenceId 和 revision 追加而非覆盖；
8. 是否展示自动复核最多一次；
9. 是否诚实区分已验证和待真实验证；
10. 是否保留开源来源和许可说明；
11. 是否没有泄露任何敏感信息；

16. 是否避免过多故障、闪白、粒子和无意义转场；
